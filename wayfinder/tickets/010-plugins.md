## Question

用户要求（m01889 / m01909）：功能要能「通过插件模块化方式集成」；并点名 Alcedo Studio 式的**项目节点配置路径 / 虚拟目录**（应用内 inode 式层级，独立于磁盘目录）作为第一个候选。
契约草案见 `docs/core-model.md` §12；内置模块的装配方式已定（[ADR 0005](../../docs/adr/0005-typescript-backend.md)）。

要定的事：

1. **内置与插件的分界**：内置能力（`jobs/*.ts`、`channels/*.ts`，随代码发布）与第三方插件（数据目录加载、独立生命周期）是同一套契约还是两套？内置先按注册表落地，插件 v1 是否就要能加载？
2. **插件能贡献什么**：候选 —— 任务 kind（`JobHandler`）、通道（`Channel`）、**虚拟目录提供者**（`FolderProvider`）、选择集新词（`Selection` term）、AI 执行者（`Executor`）、设置页表单片段。哪些进 v1 契约、哪些留缝？
3. **权限与副作用声明**：manifest 里声明副作用等级（只读 / 写标注 / 写库内状态 / 写新位置 / 写原片目录），宿主据此拒绝越权（不变量 1 与 3）。等级怎么切？
4. **虚拟目录（Alcedo 式）**：作为**默认关闭的可选插件**（不破坏「文件夹即真相」）。它的节点结构存哪 —— 应用数据目录的项目文件，还是照片目录可写时的 `.artworks/`？要不要能一键导出成真实目录结构？
5. **加载与隔离**：启动时扫描 + 重启生效（简单）vs 热插拔（复杂）；插件崩溃/超时怎么隔离（in-process vs 子进程）。
6. **接口承诺时机**：插件 API 一旦公开就是承诺 —— v1 就冻结，还是先内部留缝、宣布开源时再承诺？

产出：插件扩展面的第一版决定（哪些进 v1、哪些留缝）。

## Resolution（2026-10-08，六问全部拍板）

1. **同一套契约，v1 只加载内置**：内置（`jobs/*.ts`、`channels/*.ts` 代码内注册表）与第三方插件共用 manifest 形状，差别只在加载位置与生命周期；第三方插件加载（数据目录扫描）v1 **不做** —— 先让内置能力把契约形状磨实。
2. **v1 冻结的贡献点只有两个**：`JobHandler`、`Channel`（两者都已是注册表投影到 `/capabilities`，加一个文件就出现，前端零改动）；`Executor` 形状已定（`kind/model/local/status`）但随 push 立项才实现；`FolderProvider` / `SelectionTerm` / 设置页片段 = **留缝不冻结**（内部接口允许变）。
3. **副作用等级五档进 manifest 形状**（只读 / 写标注 / 写库内状态 / 写新位置 / 写原片目录），对齐 core-model 不变量 1 与 3；v1 宿主不做运行时强制（内置可信），第三方加载落地时再按等级拒权。
4. **虚拟目录（Alcedo 式）**：默认关闭的可选插件（v1 不实现）；结构存**应用数据目录**（照片目录只出 `.xmp` 与 `.trash` 的承诺不动）；一键导出真实目录 = 将来票，不随插件首发承诺。
5. **加载 = 启动扫描 + 重启生效**（无热插拔）；隔离 = in-process try/catch + handler 超时，子进程隔离随第三方加载再议。
6. **v1 不冻结对外插件 API**：一旦公开就是承诺 —— 等宣布开源时再冻结（届时把上表升格为公开契约）；在那之前「留缝」意味着允许不兼容变更。

对当前代码的直接影响：零（v1 插件面 = 内置注册表现状 + 本决议入档）。
