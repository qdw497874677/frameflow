# FrameFlow 飞书连接器技术计划

状态：**技术计划及任务清单已获用户确认；开始按清单实施离线风险验证**。

用户已批准 [SPEC.md](../SPEC.md)、四份模块规格及本技术计划。唯一执行清单为 [tasks/todo.md](todo.md)，已获用户确认；当前进入 Implement 的离线风险验证，不启用连接器、不改服务配置、不向飞书发送消息。

## 1. 目标与边界

完成国内飞书自建应用机器人接入：网页确认是否通过连接器投递，项目/事件策略推荐一个或多个目标；飞书图片+卡片逐张确认、查询进度、继续、重新标记及显式发送原始 JPEG。SDK 负责连接/重连/平台协议，我们负责授权、确认版本及逐目标结果。

模块 ID 保持：`connector-core`、`delivery-policy`、`feishu-connector`、`feishu-interaction`。

- 只新增官方 SDK，候选 1.76.0；锁定前验证 package 类型、Node兼容和依赖风险。
- 单 FrameFlow 服务进程、单 dataDir 写者；不引入数据库、Redis、消息中间件或可视化流程引擎。
- 旧应用内任务、API token、范围链接、选片与回收站保持兼容；新飞书任务显式携带确认模式，不改变旧任务 skipped 的既有含义。
- 真飞书联调需专用应用/目标及用户发送许可，本地通过不等于平台验收。

## 2. 现有代码核对与必须先解决的风险

| 位置 | 现状 | 本计划处理 |
|---|---|---|
| `server/src/core/marks.ts` | 先追加 MarkChange 再发布状态，异步 XMP；没有版本与操作ID，同值操作无持久记录 | 增加可重放标记事务，保留旧行读取；确认零星也能持久化 |
| `server/src/jobs/service.ts` | 每任务 inbound 串行；仅 running/interrupted 接新回流；创建随机 ID，重启 queued/running 收敛 interrupted | 内部幂等创建入口、受控确认/重标入口，不放开旧公共终态回流 |
| `server/src/core/jobs.ts` | 任务快照和事件分别追加，非法状态迁移拒绝 | 确认结果以已提交动作投影，投影重复执行不重增计数/事件 |
| `server/src/jobs/annotate.ts` | skipped 也是终态；只保存最新 clientRef | 新确认集合与动作日志，不用当前 latest-clientRef 做长期去重 |
| `server/src/core/library.ts` | 普通写标、回收站清标、扫描 XMP 基线是多条写路径 | 共同版本边界；移走/换源/扫描不能让旧卡继续写 |
| `server/src/api/auth.ts` | 管理 session、全权限 Bearer、缩略图/任务范围 token | 新管理接口只接已认证 session，旧接口凭据规则不变 |
| `web/src/features/jobs/DispatchAnnotate.tsx` | 创建任务后轮询产物链接 | 添加选择连接器/目标确认与逐目标状态，保留仅应用内 |

最先做两个风险验证：官方 SDK 卡片表单/事件/更新能否支持确认式交互；照片级版本与崩溃恢复能否在现有本地日志架构上成立。失败则先修正计划，不以削减权限或跳过冲突检查赶进度。

## 3. 模块依赖与装配

```text
connector-core（端口/目标/授权/配置）
  ├─ delivery-policy（策略预览/确认/投递状态）
  └─ feishu-connector（SDK 生命周期/媒体/事件传输）
             ↓ 由入口装配
feishu-interaction（卡片/命令/确认/游标）
             ↓
现有 JobsService / Library / MarksStore 的受控业务接口
```

`server/src/index.ts` 是组合根：注入通用端口与回调，SDK 适配器不 import 交互服务，策略不 import SDK。路由通过独立注册模块挂在现有 Fastify 实例上，避免所有实现堆进 `server/src/api/server.ts`。

共享契约先定义后并行：平台类型不越过适配边界。API线格式仍只在 `contracts/openapi.yaml` 定义，并同步 `web/src/api/contract.ts`。每次增加端点的同一小步完成状态码/输入限制/DTO/契约测试，不先堆一份无法运行的大契约。

## 4. 关键设计提案

### 4.1 管理、身份与配置

- 配置 `connectors.json`、`delivery-policies.json` 原子替换，带 revision；写入失败不发布内存新状态。
- App Secret 只读取环境变量，配置保存变量名，API只返回 secretConfigured；SDK 自带日志经净化，不能转储完整事件和认证头。
- 新连接器默认 disabled；应用密码未设置不能启用外传。管理端点要求 `via=session`，另校验同源/CSRF保护；不能因当前部署关闭密码而把所有人视作连接器管理员。
- 飞书身份固定为 connectorId + tenantId + actorId。来源群/私聊目标、项目范围、canAnnotate/canRequestJpeg/creator权限分别检查。
- 入口/帮助/首次创建不要求已有任务投递；操作既有任务则检查任务→目标关系。不能混用这两种授权。
- 有界分页、请求体大小、每次确认照片数与并发限制通过显式配置/常量纳入契约测试，不静默截断任务快照。

### 4.2 持久化与单写者

新增记录均在 dataDir，使用版本化 envelope 与稳定 ID。只依赖本机文件系统；数据目录不能位于照片网络共享。

| 存储 | 用途 | 恢复规则 |
|---|---|---|
| `connectors.json` / `delivery-policies.json` | 配置 | 原子替换；校验 revision |
| `delivery-previews.jsonl`（拟） | 10分钟预览、确认requestId、照片/目标快照及预分配jobId | 过期拒绝；确认后按记录恢复同一任务 |
| `deliveries.jsonl` | 每目标及每必要消息部分的发送意图/状态/messageId | pending可恢复；sending遗留→unknown，不自动重发 |
| `connector-sessions.jsonl`（拟） | 卡片关联、照片版本、目标游标及失效时间 | 重启可定位旧卡；过期会话拒绝 |
| `connector-actions.jsonl` | 受理/拒绝/结果，命令与JPEG意图 | 动作ID+载荷hash去重；效果是否已发生由效果日志对账 |
| `marks.jsonl` | 旧 MarkChange + 新完整标记事务 envelope | 真正落标的权威记录，包含opId/revision/结果 |
| 现有 `jobs.jsonl` / `job-events.jsonl` | 任务/进度/可视历史投影 | 根据已提交动作幂等补齐，不重新写旧标记 |

日志只把完整、校验通过且提交结束的记录重放为成功。末尾截断记录可修复并有诊断；中间损坏不能静默跳过并继续外传，应使相关连接器进入不可写/需处理状态。追加错误后的文件尾必须恢复或封锁写入，不能把下一条黏在半行后。

新提交记录使用明确 flush/fsync 边界后才确认成功。本文保证进程中断与注入I/O失败的可恢复性，不宣称任意磁盘损坏或硬件失效都不丢数据。

启用连接器前须取得 dataDir 单写者保护；用原子占用与可验证的进程身份，拒绝第二个写者。陈旧锁清理要验证PID复用，不单凭PID存在/不存在或超时自动夺锁；不能安全判定时失败关闭并提供管理说明。锁的具体实现先做故障测试，不引入额外锁库。

### 4.3 标记版本、并发与恢复协议

**版本是标注版本 + 源身份签名，不只是当前星级值。** 这样“改到3星又改回0星”、同值确认、文件同路径替换都可让旧卡失效。扫描首次基线由稳定源/标注基线生成，重启不随意变号；新事务保存持久 revision。

具体版本提案为 `(sourceGeneration, markRevision)`：每次事务持久化源签名（规范化项目/相对路径、配对文件集合与 size/mtime，必要时 inode 信息）及其 generation；同源重启沿用 generation，扫描确认签名变化则创建新 generation。这个签名不是内容哈希保证，无法检测刻意保留全部元数据的替换；需要更强保证时另行批准按需指纹。

重放先建立历史事务索引，扫描验证源身份后才能将事务状态应用到当前文件。源尚不可达时保留历史、禁止确认，不把未验证状态当成当前源可写。源不同则旧generation只供审计和旧任务确认投影，不能写新文件的XMP或直接套旧标记；旧卡冲突，刷新后展示新源基线。对同一源，已提交事务优先于XMP（可能崩溃在写XMP之前）；没有事务时沿用现有XMP基线规则。外部XMP变更不擅自覆盖已提交日志；若产品要导入该变更，需显式新事务而非扫描静默覆盖。旧无generation日志保留原兼容读取，首次参与新飞书任务时建立基线绑定，不追溯保证旧数据文件替换的识别。

新增内部 marks 事务支持 opId、expectedRevision、完整结果和可选 job确认元数据。旧 `/marks` 不必提供 expectedRevision，仍按既有覆盖规则处理，但所有成功写入必须推进/记录版本；飞书只接受带版本的确认。旧 MarkChange 仍可读取、历史 API输出仍是既有语义，不把新 envelope 原样返回给旧前端。

提交顺序：
1. 根据可信事件与服务器 session 定位动作，校验权限、任务状态和照片存在性。
2. 按统一锁顺序进入：需要任务状态的操作先 job gate，再按 photoId 排序取得 photo gate；纯普通标记只取 photo gate，持有 photo gate 时不反向申请 job gate。
3. 取得上述锁后，重新检查任务存在、terminal/undone状态、当前目标授权、照片可访问性/源generation及预期标注版本；不能仅依赖入锁前检查。job gate 保持到持久确认与投影决策确定，随后才释放；取消、撤销与旧inbound也走同一job gate。记录受理意图。相同动作重复返回 pending/既有结果，不执行第二次；同ID异载荷409。
4. 在 `marks.jsonl` 单个事务 envelope 中写入 opId、预期/新版本、完整标记状态及确认元数据，可靠提交后才发布内存。即使值不变也记录确认版本。失败则不发布成功。
5. 幂等更新确认集合和任务事件（带 sourceOpId），记录动作结果；随后异步更新卡片。
6. XMP 写失败保留警告，不撤销已提交状态；同照片 XMP 写入要有序，旧任务不能在较新标记之后回写旧值。

恢复时：动作受理但无已提交 marks事务 → 重新校验权限/版本后才可执行；已有事务但任务投影缺失 → 只补集合/事件/结果，不再次 apply旧标记。投影写失败仍保留事实，不让用户用同一次意图重复计数。连接器开放接收前先完成此恢复；未解决损坏时保持停用。

取消/撤销持有 job gate，避免确认经过校验后被取消仍写入；回收站/还原/物理删除按同一 photo gate 更新可访问性。内部 `applyMarks` 与已有 `trashOne` 清标调用需要拆为已持锁内部方法，避免重入死锁。大批量操作不在等待网络文件I/O时锁住所有项目。

### 4.4 任务确认与兼容

新飞书派发沿用 annotate kind，但增加明确的 confirmationMode/connector 元数据。旧任务仍走原先 inbound 和 settle；不把历史 skipped 推断为新模式已确认。

- 确认集合按 jobId+photoId 唯一，来源opId去重；已确认同一照片再修改只增加历史，不增计数。
- 新模式只有明确确认覆盖整个快照才完成；跳过、无权、失联不算完成。计数可从集合重建。
- 受控 re-mark 允许新模式 done 任务修改已确认项，保持完成计数；cancelled/undone 永不接受新确认。
- 任务列表/详情附加 confirmation 计数，前端明确展示；旧 progress 字段保持可读且不更改旧任务行为。
- 外部网页/旧API修改全局照片使版本失效，但不自动确认这个飞书任务。

### 4.5 确认任务只创建一次

目前 `JobsService.create()`重新展开选择集且随机分配ID，不能直接用于确认重试。增加内部 `createFromConfirmedSnapshot({jobId, requestId, snapshot, ...})`：jobId在确认记录中先固定，服务端验证ID/请求摘要；外部客户不能指定任意jobId。

将预览与已接受确认明确分态：preview 有10分钟有效期；accepted confirmation 在任务/投递去重生命周期内保存，不随预览到期删除。先按 requestId 查已接受记录，重试返回/恢复原任务，然后才对首次确认检查预览是否到期。

首次确认在单写者下由requestId gate串行、持久记录建立唯一占用：同ID同摘要返回pending/原结果，同ID异摘要409。原子接受记录绑定照片快照、目标快照、policyRevision、完整任务参数、完成通知选项及显式外传同意；权限与配置版本变化先要求重新预览。持久化requestId、不可变摘要与预分配jobId之后，才创建同一任务，再保存分目标投递意图。中断时只重放缺失步骤。同ID异内容拒绝；新策略不会改变已确认任务。仅计划模式保持不落实际任务的旧语义。

确认返回202/已受理状态与查询位置或确定的job对象；具体状态码在实现端点时进入契约，不能前端自己推断“没拿到响应就再建一个”。任务与目标授权在恢复执行时再次检查。

### 4.6 投递、多个消息部分与不确定结果

目标投递可由入口卡/挑片卡两部分组成；优先把预览嵌入挑片卡，只有平台确有需要才拆图片消息。每部分有稳定partId、intentId和SDK发送uuid，成功部分不会因下一部分失败而重发。

状态流：pending → sending → sent/failed/unknown。写 sending意图成功后才调用SDK；SDK接受后持久化messageId，再发布sent。响应超时或发送后崩溃无法判定时unknown，不靠本地计时判断失败。官方uuid仅一小时去重，不能代替永久业务状态。

V0还须核实锁定SDK的HTTP超时/内部重试/取消语义。应用超时不代表SDK请求已终止：原attempt仍执行时不得启动替代发送。保留attempt关联，迟到成功归并到原意图并保存messageId；SDK完成/可靠取消后才允许进入人工替代流程。进程重启失去本地attempt状态时仍保持unknown并先核对平台，不推断远端没发送。不自行另造重试框架。

UI支持明确失败部分重试；unknown先核对，不能核实则要求用户确认重复风险形成新的发送意图，同时保留旧unknown关联。不能因为点击重试就把整目标所有部分重发。

完成通知由稳定 completion generation + targetId派生意图，只有当时已确认的目标/通知选项可发。重新标记不会重新触发完成事件。

### 4.7 卡片与长连接

先验证官方类型与JSON样例：新版 `card.action.trigger`、可信操作者/会话字段、可提交完整星级/待删表单、toast/更新响应、群聊私聊限制、消息更新接口。

长连接回调3秒内只做有限校验和有界受理。可靠受理成功回“处理中”，不是“已保存”；受理失败/满载可解释拒绝。后续业务异步执行，结果更新卡片。优先复用SDK机制，不增加传输重试层。

session绑定 app/tenant/target/message/task/photo/version/expiry。卡片value仅携带不透明session/action引用及表单值；实际用户由SDK envelope取。转发/改参数不能访问别处任务。若可信上下文不足，拒绝并提供从机器人入口重新打开的路径。

卡片控件不写共享服务端草稿；确认读取本次提交者的表单值。按钮与文字命令复用同一个控制器服务。目标内共享游标，跨目标游标独立；照片结果全局共享。

### 4.8 媒体与原始JPEG

默认读取现有2048预览，限制图片10MB/官方分辨率；服务器直接上传，不把范围token链接泄漏给飞书下载。

“发送JPG原图”检查当前目标canRequestJpeg、任务与照片可见性，解析受控JPEG FileRef、验证实际文件/字节大小≤30MB，使用IM stream文件接口，原字节不重编码。无JPEG、视频、RAW-only、超限、失联明确拒绝。

按应用缓存媒体key，源变更失效；缓存不代替权限。请求意图日志与消息part状态复用去重规则；群文件对整个群可见需明确提示。

| V1 管理闭环 | 页面新增disabled实例/目标，配置脱敏，权限拒绝；假适配启停 | V0端口 | CC-01～09 |

| V3 飞书传输 | SDK适配长连接、卡片/预览传输、逐部分结果与失效恢复 | V1端口、V2投递 | FC-01～06 |

## 8. 风险、回滚与数据兼容

| 风险 | 防护/回退 |
|---|---|
| SDK表单或回调上下文不支持所需交互 | V0先验证，真实V7再验；不偷偷换Webhook/取消授权 |
| 多文件状态不是数据库事务 | 单权威标记事务+幂等投影+故障重放；无法恢复时拒绝新外传 |
| 老版本不识别新marks事务 | 上线前备份整个dataDir；旧行可读但新写格式不宣称可直接降级；回滚先停服务，导出兼容标记或恢复备份，说明恢复点后的变更影响 |
| 原图/预览外传不可逆 | 明确确认、目标allowlist、按需JPEG、取消不宣称能收回已发媒体 |
| 发送超时引发重复消息 | unknown状态+人工确认重复风险；不依赖一小时uuid做永久去重 |
| NAS拖慢回调 | 回调快速可靠受理，慢I/O独立执行；有限并发/超时，无同步网络FS |
| XMP较旧写入覆盖新写入 | 单照片有序副作用，恢复只写最新确认状态；告警不隐瞒 |
| 配置/密钥日志泄漏 | 环境变量引用、输出脱敏、事件日志白名单字段、负向测试 |
| 假进度导致误判完成 | 独立明确确认集合，不将跳过/失败算确认；计数可重建 |

默认不开启外传。先通过假SDK闭环，再一个测试实例/一个目标，最后扩展到多目标。停用实例切断新外传和交互，保留任务/日志便于审计；不删除数据作为回滚手段。
