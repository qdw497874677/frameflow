# 项目就是磁盘上的一个目录：不导入、不导出

状态：已接受（产品骨架阶段，用户主动砍掉 LR 式导入/导出工作流）

## 背景

照片已经在磁盘上按既有的习惯分好了：项目目录（一次旅行 / 一次拍摄）→ 按设备 → 照片|视频 → 原始|修改后。
应用的价值集中在两头：**快速挑出喜欢的与待删的**，以及**把选中照片按规则归位**。

中途曾认真考虑照搬 Lightroom 的三段式工作流：把卡里的素材「导入」进来（复制 / 移动 / 只是登记，
可选改名、可选导入后删来源），挑完之后「导出」到指定目录（可转格式、可调长边、可套导出预设）。

## 决定

不导入、也不导出。

- **「项目」= 用户在应用里映射进来的一个目录**（一个路径 + 一个显示名）。应用扫描它下面（含子目录）的照片，
  就当这一个项目来标记与删除。
- 原文件只被两种操作碰到：**写标记**（星级 / 待删，落 XMP）与**归档时的移动**。绝不复制、绝不转换、绝不产出衍生文件。
- 出图（转格式、调尺寸、交付）不是本产品的职责：交给 Lightroom / darktable，或者用归档把它放到你要的目录。

## 备选方案

- **LR 式导入**（复制 / 移动 / 登记）：多一次复制、多一份需要与来源对账的状态；而用户的目录早就分好了。
  「导入后删来源」是个不可逆的破坏性动作，产品还得为它设计校验与回滚。
- **LR 式导出**（生成 JPEG / 尺寸 / 质量 / 滤镜）：等于在应用里内置一套渲染与调色管线，
  直接踩进色彩管理、RAW 解码一致性、滤镜生态这些深水区 —— 而它们和「挑片」的价值主张毫无关系。
- **只做导入的「登记」形态**（Add）：最轻，但仍然引入「库」与「磁盘」两份需要同步的认知，
  而它换来的只是「知道有哪些照片」—— 扫描一遍就能知道。

## 后果

- 应用永远不产生第二份真相：不复制、不转换；卸载它，磁盘上什么都不变。
- 预览与缩略图仍要从 RAW 出图（票 001 的分层管线），但那是**缓存**，可以随时删掉重建，不是交付物。
- 挑完之后要交付给别人时，用户得自己动手 —— 本产品只负责让磁盘上的照片各就各位。
- 若将来真要做导出（比如一键出长边 2048 的 JPEG 给客户），那是一次 **destination 重画**：
  要连带处理色彩管理、与「修改后」目录的关系、以及导出记账。它不会作为本图的雾自动长出来。
