# 项目就是磁盘上的一个目录：不导入、不导出、不搬动

状态：已接受（产品骨架阶段；用户先后砍掉 LR 式导入/导出与归档，m01551 / m01565 / m01572）

## 背景

照片已经在磁盘上按既有的习惯分好了：项目目录（一次旅行 / 一次拍摄）→ 按设备 → 照片|视频 → 原始|修改后。
应用的价值收敛到一件事：**快速标注出喜欢的与待删的**，并让待删的有个可还原的去处。

中途走过两次弯路，都留下了记录：

1. **LR 式三段式工作流**（导入 → 挑 → 导出到指定目录）：把卡里的素材「导入」进来（复制 / 移动 / 只是登记），挑完之后「导出」。
   用户先要求「原素材不产（不动），除非明确勾选删来源」，随后直接否掉：「还是简化为原有的模式，直接映射指定目录的所有照片文件，作为一个项目，进行标记和删除。不用导入导出模式了」（m01551）。
2. **按规则归档**（条件匹配 + `{root}/{project}/{device}/{kind}/{variant}` 目标模板 + 先预演再原子移动，
   规范见 `contracts/rules.md`，语义见 ADR 0002）：被用户判定为不需要：「文件夹我可以先整理好，只需要导入文件夹扫描所有照片进行标记就可以了」（m01572）。

## 决定

不导入、不导出、不搬动。

- **「项目」= 用户在应用里映射进来的一个目录**（一个路径 + 一个显示名）。应用扫描它下面（含子目录）的照片，
  就当这一个项目来标记与删除。文件夹由用户自己先整理好，应用不做归位决策。
- 应用只写两处磁盘：**标记**（星级 / 待删，落 XMP）与**回收站**（移入 `dir/.trash`、还原、显式确认后真删）。
- 出图（转格式、调尺寸、交付）与「把挑好的照片交到别处」不是本产品的职责：交给 Lightroom / darktable，
  或操作系统层面的复制。**导出**推迟到后续（记在 wayfinder 的 Not yet specified），当前不做。

## 备选方案

- **LR 式导入**（复制 / 移动 / 登记）：多一次复制、多一份需要与来源对账的状态；而用户的目录早就分好了。
  「导入后删来源」是个不可逆的破坏性动作，产品还得为它设计校验与回滚。
- **LR 式导出**（生成 JPEG / 尺寸 / 质量 / 滤镜）：等于在应用里内置一套渲染与调色管线，
  直接踩进色彩管理、RAW 解码一致性、滤镜生态这些深水区 —— 而它们和「挑片」的价值主张毫无关系。
- **按规则归档**：本来是最有差异化的部分（市场上确实没有「筛选后按规则分发到目录」的开源产品），
  但它把产品拖进「规则 DSL + 预演 + 原子移动 + 撤销记账 + 规则编辑器」一整套机器，
  而用户的实际操作是「文件夹我自己先整理好」。**用不到的能力就是负债**：它已经被实现到可演示，
  仍然整体删掉（见票 003 的结束说明），而不是留着一个半死的页面。

## 后果

- 应用永远不产生第二份真相：不复制、不转换、不搬动；卸载它，磁盘上什么都不变（除了星标 XMP）。
- 预览与缩略图仍要从 RAW 出图（票 001 的分层管线），但那是**缓存**，可以随时删掉重建，不是交付物。
- 挑完之后要交付给别人时，用户得自己动手。
- 若将来真要做导出或归档，那是一次 **destination 重画**：要连带处理色彩管理、与「修改后」目录的关系、
  以及导出/移动记账。它不会作为本图的雾自动长出来。
