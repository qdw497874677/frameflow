# 以磁盘文件夹为真相，不做导入式媒体库

状态：已接受（历史决策 003 期间落定，原记录可查 Git 历史，源自更早的一张「自用还是开源产品」的选型结论）

## 背景

市面上的照片管理产品几乎都是**库中心**的：Immich、PhotoPrism、Lychee、LibrePhotos 都要先把照片**导入**，
复制进自己的存储布局，再自建数据库登记每一张、生成缩略图、管理相册与用户。原文件一旦被它们接手，
目录结构就归它们摆布，用户看到的「文件夹」是数据库的一个视图。

这个产品的诉求相反：拍摄成果已经在磁盘上有一套自己长出来的结构（项目 → 设备 → 照片|视频 → 原始|修改后），
而用户的其它工具（Lightroom、digiKam、访达）也在看同一批目录。

## 决定

应用**直接读写用户已有的目录结构**：

- 不导入、不搬动照片；根目录是「注册」而不是「导入」。
- 唯一的自有状态是**标记**（星级 / 待删，写进 XMP 与主文件同住）和**配置**（规则、别名、项目名记忆）。
- 预览与缩略图现场生成并缓存，缓存可随时重建；它不构成真相。
- 每次扫描都重建「有哪些照片」，不维护「库里有什么」的台账。

## 备选方案

- **导入式媒体库**（跟随 Immich / PhotoPrism）：可换来强搜索、去重、多用户，代价是用户交出目录主权，且与其它工具打架。
- **数据库为主、磁盘为副本**：状态丰富，但立刻要面对「库与磁盘不一致」这个永久的二等公民问题。

## 后果

- 用户随时可以用别的工具看同一批文件；卸载应用不会丢任何数据。
- 不需要维护两份真相之间的一致性。
- 不能假设文件名或目录结构稳定 —— 照片可能被其它工具改名、移动，所以每次扫描都要重建，标记必须存在文件侧（XMP）。
- 没有免费索引：搜索、去重、跨目录的「所有 5 星」这类查询要现场扫描，v1 不做。
- 缩略图管线的正确性变得关键（历史决策 001 的分层预览就是它的直接产物）。
