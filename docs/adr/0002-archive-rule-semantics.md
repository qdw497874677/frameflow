# 归档规则：首条命中即停、永不覆盖、成组原子移动

状态：已接受（wayfinder 票 003）

## 背景

归档要回答三个躲不开的问题：

1. 多条规则同时命中一张照片时，听谁的？一张 5 星的视频既满足「喜欢的 → 修改后」也满足「视频 → 视频目录」。
2. 目标目录已经有同名文件时怎么办？重拍的照片、二次导入的照片都可能撞名。
3. 移动的单位是什么？RAW + JPEG 双出，旁边还躺着 Lightroom 写的 `.xmp`。搬走主文件却留下 sidecar，等于毁掉用户的全部调整。

## 决定

- 规则**有序**，从第一条开始判定，**首条命中即停**（first-match-wins）。
- 同一条规则内：不同条件是 AND，同一条件写数组是 OR。
- 冲突默认**追加序号**（`-1`、`-2`…），可配 `skip`，**永不覆盖**。
- 移动的最小单位是**组**（主文件 + 影子文件），组内原子：要么整组过去，要么整组不动。
- 执行前先**预演**（只读），执行后落**移动日志**；「撤销」按钮留 v1.1，日志先落地。

## 备选方案

- **全部命中就依次叠加动作**（像防火墙的 NAT 规则链）：表达力更强，但「这张照片最后在哪」需要模拟整条链才知道。
- **按规则优先级合并多个动作**：同一张照片可以既移动又改属性，代价是顺序、冲突、幂等都变成组合爆炸。
- **冲突时覆盖**：省一个后缀，代价是不可逆的数据丢失。
- **只移动主文件、sidecar 单独交给用户**：实现最省事，也最容易悄悄丢调整。

## 后果

- 「这张照片为什么去了那里」可以一眼回答：顺着列表往下读，第一条命中的规则就是答案。
- 归档永不毁数据：最坏情况是留下一个重复文件（`-1` 后缀）让用户自己清理。
- `.xmp` 不会与主文件分离 —— 这张票最容易被低估的价值。
- **规则顺序成为语义的一部分**：UI 必须能排序，而且不能自动重排（自动排序会悄悄改变归档结果）。
- 想表达「既要 ≥3 星去修改后、又要视频去视频目录」必须写成两条规则并注意先后，规则列表会比「条件叠加」的世界长一点。
