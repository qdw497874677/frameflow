# 动作层统一为任务（Job），事件只做日志

状态：已接受（2026-09，随用户 m01709 / m01715 的问题定下；完整模型见 [docs/core-model.md](../core-model.md)）

## 背景

用户提出三件事，本质是一个问题：产品怎么从「挑一批照片」长成「标注 + 按标注触发删除 / 导出 / 滤镜处理，将来还能把批注任务推到飞书或别的客户端」。

- m01709：「核心就是给照片标注，浏览。然后可以根据标注进行删除照片或者导出，自己后续触发设置好的其他处理任务比如设置滤镜之类的。通用的功能应该就是，照片扫描，标记，处理，导出，删除这些功能流程。」
- m01715：「是否需要引入工作流以及事件驱动，并且每个功能做到模块化」
- 更早（m01633）：整个原片过程类似「标注」，要设计好工作流，后续支持把任务推送到 IM（飞书）/ 其他客户端，要设计通用 API 与流程。

此时手上有一个刚砍掉归档的前端 + 一份只有同步端点的契约。要决定的是**骨架的形状**，而不是某个功能怎么实现。

## 决定

1. **两层**：扫描 / 浏览 / 标注是**状态层**（同步、廉价、改了就算）；删除 / 导出 / 处理 / 推送批注是**动作层**（异步、有产物、要进度与撤销）。五个动词不并级。
2. **动作层统一为「任务 (Job)」**：一个一等实体 + 一个 `JobHandler` 契约（`validate → plan → apply → undo?`）。新增能力 = 新增一个 kind，不动前端。
3. **选择集是可序列化的谓词**，不是 id 清单；任务是「谓词 + 操作 + 参数」。
4. **要事件日志，不要事件总线**：`MarkChanged` / `JobChanged` 追加落盘，进度走 SSE；**不引入**消息队列。
5. **不要工作流引擎**：状态机线性（planned → queued → running → done/failed/cancelled），串联用 onDone 规则，不做 DAG 编排。
6. **标注变更带来源与时间**（by / at / channel / from→to）—— 外部批注回流与审计的前提。

## 备选方案

- **按动词平铺六个功能模块**（scan / browse / mark / process / export / delete 各一套）：最直观，但会得到六套各自的「进度 / 日志 / 撤销 / 预览」实现，且将来「导出成飞书周报」这种组合无处安放。
- **通用工作流引擎**（DAG 或状态机 DSL + 重试 / 补偿策略）：服务的是**机器编排**的多步流程；我们是人推着走 + 单任务长循环，引擎带来的抽象（编排可视化、补偿事务）没有对应的真实问题，却会稀释「先预演再执行 + 有 manifest」这条纪律。
- **事件总线 / 消息队列**：给了「将来多 worker 并行」的想象空间，但当前单用户单进程，代价是消息顺序、丢失、重放这些新问题。
- **只做同步端点，不做任务实体**：最省事，但导出/处理/推送天然是长动作，进度只能靠轮询各自接口，且「我改过什么」无处可查。

## 后果

- 契约会长出 `/jobs`、`/channels`、`/marks/history`；`/trash` 保留为同步便捷入口（等价于即时 `trash` 任务）。
- 前端在第一个异步能力出现前**不需要**任务页；端口从 `PhotoSource` 拆成 `LibrarySource` + `JobSource` 时才动。
- 新增能力的成本被钉在「一个 handler + 一个 kind」，前端零改动。
- 滤镜不会被做成独立管线，而是 export 任务的 recipe 参数。
- 事件日志不可重建（XMP 只有最终状态），所以它要跟着备份策略走 —— 但丢了也只损失历史，状态仍从 XMP 重建。
